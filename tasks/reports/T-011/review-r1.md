Additional checks:

- **Server timeouts (T15).** A slow-loris probe that drips headers every 2 s against the real `main.ts` got `408 Request Timeout` after about 29 s. `headersTimeout` is in effect; the observed delay comes from Node's default 30 s `connectionsCheckingInterval` (R1-06).
- **Allowed-origin before body parsing (declared deviation).** I accept it. The Origin check runs before `express.json`, and `jsonBody()` puts `requireJson` (415) before the parser. Compared with `architecture.md` §5.2 step 4, the only observable differences are:
  - a foreign-origin POST gets 403 instead of 400/413/415;
  - a foreign-origin POST to an unknown path gets 403 instead of 404.

  Per-client limiters still run after both checks in either order, so limiter counting is unchanged. A foreign site can no longer make the server buffer or parse a body. This is stricter, not looser. `architecture.md` §5.2 needs a one-line doc update (orchestrator notes).

- **`clientIpSource` option on `createClientLimiter`.** I accept it. The limiter has no other clean way to reach the configuration, and a required field means no route can silently fall back to `socket` in production. But `AppDeps.clientIpSource` is now dead (R1-02).
- **`CONTACT_PHONE` optional outside production.** I accept it. `.env.example` ships the fixture, production requires the variable, and E.164 is validated whenever it's set. T-018 must handle `undefined` in dev and test explicitly (orchestrator notes).

## Notes for orchestrator

- **Doc drift (architecture §5.2 step 4):** the implemented order is CORS → allowed-origin (all POSTs, global) → per-route `jsonBody` (`requireJson` 415 → `express.json` 400/413) → limiters. I accepted it as stricter. Please update §5.2 so T-014/T-015 implementers don't re-add a per-route Origin check after parsing.
- **Doc drift (testing.md §2):** `Clock.now(): number` (R1-04). Recommend updating the doc to match.
- **Task file validation command:** `pnpm --filter @portfolio/server test -- --coverage` doesn't forward the flag (pnpm passes `--` through as a literal arg, and vitest ignores what follows). Use `pnpm --filter @portfolio/server exec vitest run --coverage` in future task files, or add a `test:coverage` script.
- **T-010 follow-up:** swap the server-local `ApiErrorCode` (`http/respond.ts:7-19`) for the contracts import once T-010 merges. It matches `api.md` §1.1 exactly today.
- **T-012:** replace `checkDatabase: () => undefined` in `main.ts:35` with `SELECT 1`, and register the DB close as an `onShutdown` hook Hooks run in reverse registration order, so register the DB-close hook **before** the server-close hook. That way the server stops accepting and draining requests first, and the DB closes last.
- **T-018:** `config.contactPhone` is `string | undefined` outside production; the phone route must handle `undefined` (for example 503 `VERIFICATION_UNAVAILABLE`, or use the fixture in tests).
- **T-050:** every production refusal triggers only when `NODE_ENV=production`. If Railway starts the container without it, the API boots with fakes and http origins. The Dockerfile must set `NODE_ENV=production`. Consider an ops-checklist line or a guard (for example refuse `CLIENT_IP_SOURCE=x-real-ip` unless production). Hardening idea, not required by any doc: in production, refuse `TURNSTILE_ALLOWED_HOSTNAMES` containing `localhost`.
- **Windows:** real OS signals can't be delivered to a Node process on Windows (`taskkill` without `/F` doesn't raise SIGTERM). Shutdown was verified by emitting `SIGTERM` in-process on the real `main.ts`; a Linux SIGTERM check belongs to T-050 (`docker stop`).
