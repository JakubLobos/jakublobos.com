# ADR-0017: Live guestbook submission status with general reasons

- **Status:** Accepted (owner decision, 2026-10-27) · **Amends:** [ADR-0005](0005-openai-moderation-with-local-rules.md) (uniform modal) · **Related:** T-036, `guestbook-moderation.md` §2, §4, §10, `api.md`, `security.md` T5

## Context

ADR-0005 and the T-029 spec made every submission look the same to the visitor: a uniform "in review" modal, whether the note was reviewed, silently dropped or superseded. That protects the filters from probing, but the visitor never learns what happened. The owner wants live progress and an outcome in the modal: checking, then approved, rejected (with a very general reason), superseded, or "taking longer".

## Decision

1. **Lookup key = the existing `clientRequestId`.** It is a random UUID generated by the browser and already stored (UNIQUE). It is unguessable, so it works as a capability token. Sequential ids are never used. The endpoint validates the UUID format (400 otherwise).
2. **Endpoint** `GET /api/guestbook/submissions/:clientRequestId` returns `{ data: { status: 'pending' | 'approved' | 'rejected' | 'superseded', reason?: 'inappropriate' | 'off_topic' | 'impersonation' | 'personal_data' } }`. Unknown or expired tokens get 404. The response never contains the text, scores, categories, provider names or internal reasons. It has its own per-client limiter (30 / min) and `Cache-Control: no-store`.
3. **Very general reasons**, mapped server-side by a pure `domain` function (`rejection-reason.ts`):
   - `inappropriate`: moderation reject; `offensive_or_rude`, `sexual_or_suggestive`, `political_or_religious`, `negative_about_owner`, `spam_or_ads`, `self_promotion`; blocked terms other than meme tokens.
   - `off_topic`: `low_effort_or_meme`, `off_topic_or_weird`, `gibberish`, `other`; the silent quality rules; meme blocked terms.
   - `impersonation` and `personal_data` map to themselves.
4. **Outcome rows.** Rejected and superseded rows are still deleted (I-4). A new table `guestbook_submission_outcomes (client_request_id PK, outcome, reason, created_at)` keeps a text-free record so the endpoint can answer. It holds no text, hash, IP or user agent. Rows follow the 24 h pending retention and the table is capped at 1000 rows.
5. **Silent drops** (quality rules, blocked terms, honeypot, recently rejected) were stored nowhere. They now write an outcome row `rejected` with the mapped general reason, and still answer 202 to the POST, so the POST stays indistinguishable. A duplicate (same token, or same text under a new token) writes nothing: the first token keeps its own status, and the other gets a 404.
6. **Frontend.** The modal polls (1.5 s, 2 s, 3 s, then every 5 s, 60 s total, 8 s per request, paused while the tab is hidden) and shows checking, approved, rejected with the localized reason, superseded, or taking longer (also used for 404). The token is kept in `sessionStorage` only, so a reload within 2 minutes resumes quietly and never re-polls on later visits. An approval refetches `/api/guestbook/latest`.

## Consequences

- **Probing risk.** A visitor can now learn whether a text passed. The status leaks one of four coarse labels, never which filter fired. The probing budget is bounded by the submission limits (3 / 10 min and 10 / day per IP, 20 / h and 50 / day global), by the near-identical reason groups, and by dedupe plus the in-memory recently-rejected hashes. Accepted by the owner. See `security.md` T5.
- The uniform-modal rule of ADR-0005 no longer holds for the dialog. It still holds for the POST response (always 202 for anything that passes validation).
- A new migration (`0002`). Backups already cover the database file.
- The stricter outcome is a design addition recorded as D-29 in `open-questions.md`.

## Alternatives considered

| Option                                            | Why not                                                            |
| ------------------------------------------------- | ------------------------------------------------------------------ |
| Keep the uniform modal                            | The owner wants feedback                                           |
| Sequential `public_id` or row id as the key       | Guessable; lets anyone read other visitors' outcomes               |
| Detailed reasons (the internal reason enum)       | Makes the filters trivial to probe and tune against                |
| Server-sent events / WebSocket                    | A static-asset site with one small API; bounded polling is simpler |
| Keep rejected rows (with text) to answer the poll | Violates I-4 and stores text that must not be kept                 |
